# 外部学习（现成复用与机制萃取）

## 目标

在 Skill 生产流程中回答两类问题：是否已有可直接复用的能力（分支 A）；成熟项目的机制能否改变本轮设计（分支 B）。两个分支都要求来源可归属、结论带边界，不把外部内容无差别搬进候选。

## 调度接口

本 Skill 以分支为单位被 skill-orchestrator 调度。下表是分支契约的单一事实源；编排方的索引文件仅作摘要。

| 分支 | 调度条件 | 所需输入 | 专项产出 | 完成条件 |
|---|---|---|---|---|
| A 现成复用 | 需要判断已有能力能否复用，避免重复建设 | 任务卡中的重复任务描述与复用范围 | 候选清单、质量依据、推荐或无结果说明、采用/改写/自研建议 | 团队工作区与外部生态均已检索，或明确记录某侧不可访问及原因 |
| B 机制学习 | 标杆侦察发现可靠 GitHub 项目，且其机制能改变本轮设计 | 侦察结论中的候选项目线索 | 项目机制、适用边界、来源归属、不可直接迁移部分 | 至少深读一个确认项目的核心材料，萃取结论可供下游直接引用 |

编排调度约定：仅接受 skill-orchestrator 经路由卡指定的分支；未指定分支时，按任务卡判断并说明选择理由。两个分支的产出都必须进入交接卡的"标杆来源和可复用机制"字段。

## 分支选择

- 问题形如"有没有人已经做过类似的 Skill / 能不能直接装一个"→ 分支 A。
- 问题形如"这个领域的成熟工具是怎么解决结构、流程或质量问题的"→ 分支 B。
- 两者都可能成立时先执行分支 A：有可直接复用的能力时，不再重复学习机制。

## 分支 A：现成复用

### 检索顺序

1. **团队工作区**：列出固定工作区已安装的 Skill，按 name 与 description 匹配任务描述；命中即优先评估复用或改写，不再检索外部。
2. **外部生态**：优先使用 skills.sh 生态（`npx skills find "<query>"`，环境无 npx 时降级为网页搜索并记录降级）。查询词先用中文，无结果再用英文同义词。

### 筛选与产出

筛选依据：安装量或星标、来源信誉（官方、知名组织、主项目背书）、与任务的匹配度。不凭记忆推荐包名；所有候选必须来自当次实际检索结果。

产出候选清单（最多 3 个，含质量依据）与明确建议：直接采用、改写复用或自研。无可信候选时写明"无可靠候选"及搜索范围。

安装或改写任何外部 Skill 前，遵循平台与团队的安装审查要求；审查未通过或不可确认时，只输出候选信息，不执行安装。

## 分支 B：机制学习

### 核心原则

从优秀项目中**学习知识，而不是包装工具**。目标是把成熟项目的流程结构、质量控制和错误处理经验转化为 Skill 的行为规则；如果任务本质是"把某个工具包一层"，应停止本分支并提示重新评估 Skill 的必要性。

### 流程

1. **搜索候选**：按任务关键词搜索 GitHub 项目；以相关性、主项目背书、社区验证（星标、维护状态）排序，给出 1-3 个候选及理由。
2. **确认**：采用某个项目的结论前经使用者确认；未获确认时本分支标记为"未完成"，下游不得引用其结论。
3. **深读**：按 `references/mechanism.md` 的清单阅读确认项目的核心材料，不止于 README。
4. **萃取**：输出可迁移机制、适用边界、来源归属（项目名、链接、版本或提交）和不可直接迁移部分（语言绑定、运行时依赖、平台特性等）。

### 红线

- 每个萃取结论必须有可点击的来源归属；禁止无来源的"最佳实践"式转述。
- 不复制项目的许可证文本、凭据、大段代码或大文件进 Skill；只提炼结构与决策规则。
- 无法判断许可证或来源合规性时，标注风险并仅作思路参考。

## 详细清单

- 分支 A 的检索与筛选细则：`references/reuse.md`
- 分支 B 的深读清单：`references/mechanism.md`

进入对应分支时再读取，不提前加载。
