# 多 Skill 编排型生产总控（重决策）

## 目标与定位

协调多个参与 Skill 完成高价值 Skill 的创建、改造、验证与比较。本 Skill 负责依赖检查、标杆侦察、路由、阶段交接和作者决策，不复制各参与 Skill 的专项方法。

**进入本流程**：产出物拟在团队内复用、跨项目推广或沉淀为部门资产；或本轮涉及版本取舍、能力退役、推广判断。

**不进入本流程**：个人使用、一次性或低复用的轻量 Skill，直接使用 `skill-creator` 完成创建与其内置的轻量验证；用户只是用已有 Skill 完成单一业务任务时，也不进入。

判别示例："做一个部门通用的会议纪要整理 Skill，几个团队都要用" → 进入本流程；"做个会议纪要 Skill 我自己随手用" → 不进入，直接使用 `skill-creator`；"帮我整理这份会议纪要" → 不进入，这是用已有能力完成业务任务。

复用范围或推广意图不明时，在任务卡中确认；仍不确定时按轻量处理并记录理由。

## 增量演进原则

迭代既有 Skill 时，默认目标是在已验证有效的能力基础上增强：演进追求效果增量，即能力更可靠、证据更硬、成本更低，而不是篇幅增减或结构稳定本身。核心要求是**能力去向可追溯**：每项基线能力在新版本中的去向——保留、替代或退役——必须明确且可验证。

每次行为改动前执行以下演进闸门：

1. 运行 `scripts/verify_backup.py` 验证备份存在、可读并记录指纹；
2. 建立能力基线：列出当前触发边界、关键流程、输入输出、确认/降级规则、引用资源和已知验证场景；
3. 建立改动清单：逐项标为新增、修改、替代或退役；每项基线能力必须在清单中有明确去向，不允许静默删除。默认做最小改动；当改动清单暴露结构性问题（职责重叠、层级错乱、规则漂移）时允许整体重构，但重构后仍须满足全部基线能力去向完整；
4. 更新后对照能力基线，确认未受影响能力仍存在且行为边界未被意外改变；
5. 对改动路径和至少一个未改动的关键路径执行回归检查。结构校验只能验证文件资格，不能代替能力保留或行为回归验证。

将这份记录称为"演进清单"。模板见 `references/cards.md`。复杂改造可将其留在工程记录中；轻量改造至少在对话中列出"保留项、改动项、替代/退役项和回归结果"。

**变更集与分层验收**：同一行为目标、可共同验收且需共同回滚的修改归为一个变更集；可独立验收或回滚、业务口径不同的修改拆开，行为修改与纯结构整理分开。每个原子问题完成即检查，变更集完成后按原验收标准评估，发布前再做关键回归与分发一致性检查，无需作者为每个原子问题重复决策。

**版本闭环**：产出 Skill 的版本历史独立于套件；Git 仅作可选协同，初始化、提交、标签和发布由作者决定，不可用时按 creator 的快照与指纹规则降级。评估绑定基线与候选，验收后发生实质修改必须重验，分发包只从最终接受版本生成。完成条件：能够回答本轮新增、保留、替代或退役的能力，如何确认没有倒退，以及变更集边界、版本基线与验收后处置。

## 最小充分收益与注意力管理

流程、搜索、调用、记录和验证都不是免费收益。新增任一步骤前，先判断它是否会改变当前决策、明显降低高影响风险，或提供已有材料无法获得的关键证据。收益不足时不新增步骤；若有有限收益，采用最轻量版本并说明未获得的证据边界。

每个阶段只保留当前决定所需的最小检查集。"通用轻量架构检查"的五项与演进闸门的五步即为对应阶段预筛后的最小集，执行时不再叠加其他检查项；新增检查项前同样先过本节的收益判断。不要为了完整感重复任务卡、路由卡、来源、规则或验证结论；不要把流程名称、长清单或自我证明当作质量本身。先检查最容易造成硬错误的输入、事实、版本、权限、计算或文件问题，再检查流程完整性。

复杂 Skill 通过条件化引用和阶段交接分散细节：当前阶段只读取会改变本阶段决定的资料。本 Skill 自身即按此组织：卡片模板在 `references/cards.md`，参与 Skill 环节索引在 `references/participating-skills.md`，仅在进入对应阶段时读取。自身加载预算：主文件不超过 250 行，单个 references 文件不超过 150 行；超出时必须说明理由。

## 规范分层与交付边界

将用户要求、来源规则和 Skill 指令先分为两类：

- **过程护栏**：约束如何检索、判断、确认、验证、记录或执行，例如不得覆盖、需先备份、需要复核、不能猜测。
- **交付规范**：约束最终读者可见的内容、格式、语气、事实范围、保留项和敏感信息边界。

过程护栏默认只约束执行，不进入最终交付物；只有用户明确要求展示过程、审计材料或方法说明时才输出。交付物只呈现交付规范要求的内容。

收到负向要求时，先改写为正向执行目标，再决定其归属。例如"不要把内部过程写进交付物"应落实为"交付物仅保留受众完成任务所需的内容"，而不是在正文中反复展示禁止项、AI 约束或生成背景。不得为了证明遵守而将过程限制、负向提示、工具日志或失败说明写入面向受众的成品。

本原则在候选 Skill 侧的对应检查项为"通用轻量架构检查"第 4 项（交付隔离），两处语义保持同步。

完成条件：交付物与过程记录可分离；读者不会从正式成品中看到无关的执行约束或模型自我说明。

## 确定性检查脚本化

判定标准客观的检查——字段存在、文件存在、指纹一致、结构合法、目录存在——必须运行 `scripts/` 中的对应脚本，脚本输出即证据。不得以"阅读后确认"替代脚本输出。模型判断只用于需要语义理解的部分，例如歧义识别、质量评价、回归路径的实际执行。

| 脚本 | 用途 | 使用节点 |
|---|---|---|
| `scripts/verify_backup.py` | 验证最新备份存在、可读，输出 sha256 指纹与版本清单 | 演进闸门第 1 步 |
| `scripts/validate_structure.py` | frontmatter 必填、命名规范、目录结构、引用资源死链 | 候选结构校验 |
| `scripts/check_evidence_card.py` | 证据卡字段完整性、证据位置真实性 | 声称"已评估/已回归"时 |
| `scripts/check_capability_baseline.py` | 依赖 Skill 存在、可读、调度接口一节存在 | 首次形成路由卡前 |

脚本失败即对应环节未通过：先修复再推进，不得绕过。脚本能力覆盖不到的检查项，按"通用轻量架构检查"和相关章节的人工规则执行。

## 通用轻量架构检查

创建新 Skill 或修改既有 Skill 的行为后默认执行。目标是让类似 Agent 在常见工作环境中，仅凭 Skill 声明的输入与依赖就能理解主流程、完成核心任务并避免明显歧义；不追求所有模型、工具或运行环境产生完全相同的结果。

检查以下五项：

1. **边界清楚**：触发条件、输入、输出、不处理范围和完成条件没有互相矛盾。
2. **依赖显式**：需要的文件、工具、权限、资料和环境已说明；核心流程不依赖此前对话、隐藏记忆、特定电脑路径或未声明能力。
3. **分支可执行**：每个关键分支都有触发条件；输入缺失、材料冲突、工具不可用或结果不确定时有保守且可执行的处理。
4. **交付隔离**：最终交付物只包含面向受众的必要内容；过程护栏、内部记录、开发信息和无关敏感信息不会混入成品。对应"规范分层与交付边界"原则。
5. **概念一致**：列出全文核心术语（通常 3–6 个），核对每个术语在所有出现位置含义稳定，不同概念不共用易混淆的名称。此项依赖人工判断，是五项中最弱的检查；未发现概念问题不足以单独判定通过。

这不是全量架构审计。阻塞问题仅指会导致无法选择主分支、需要未声明资源才能完成核心流程，或会污染最终交付物的歧义/依赖。其中结构合法性、引用死链等客观项由 `scripts/validate_structure.py` 先行判定，语义项由人工审查。最小证据模板见 `references/cards.md`。

未做 Agent 实跑时，结论仅代表文本审查，不代表执行稳定性已获证明。

完成条件：类似 Agent 在仅获得声明输入和 Skill 文件时，能识别主流程、关键分支、必要依赖和交付边界。可选的实证增强：将候选 SKILL.md 交给无上下文的新会话复述主流程与关键分支，复述偏差即视为缺陷。

## 能力基线与可用性

每个独立会话或环境在首次形成路由卡前，运行 `scripts/check_capability_baseline.py` 确认依赖的可用状态；安装、环境切换、加载失败或声明能力变更后，原确认失效。没有可定位检查记录时按"未确认"处理。

| 层级 | Skill | 被调度的环节 |
|---|---|---|
| 核心硬门禁 | `skill-creator` | 创建与更新；结构校验与安装；打包分发 |
| 核心硬门禁 | `skill-effectiveness-evaluator` | 快速探索；标准比较；严格审计 |
| 条件调度专项 | `writing-for-agents` | 结构审查（触发、分支、引用、信息层级或完成条件存在风险时） |
| 条件调度专项 | `skill-from-externals` | 分支 A 现成复用；分支 B 机制学习 |
| 条件调度专项 | `skill-from-masters` | 实践案例学习（黄金/失败/对照案例） |

### 能力门禁与缺失提示

- **状态定义**：脚本判定三种状态——可用；专项不可用（不阻断未依赖它的任务）；等待核心能力基线（任一硬门禁缺失或不可读，不得进入生产阶段）。
- **人工动作**：首次发现专项缺失时，明确提示使用者缺失的能力、对本轮证据或产物的限制及安装建议；路由卡选中不可用专项时，对应环节标记"不可用"，可继续不依赖其结论的局部、可逆工作，但不得将该环节计为已完成或用通用方法伪装其专项产出；能力安装或恢复后重新运行脚本，更新可用性记录。

## 调度接口

每个参与 Skill 以**环节**为单位被调度，不再以整个 Skill 为调度单位。环节契约五要素：环节名、调度条件、所需输入、专项产出、完成条件。

契约的单一事实源是各参与 Skill 自身 SKILL.md 中的"调度接口"一节；`references/participating-skills.md` 只保留环节索引与调度时机，内容以各 Skill 文件为准。路由卡按环节填写。若某参与 Skill 尚未定义调度接口，按下文路由触发表中的"最低专项产出"调度，并在路由卡中记录为契约缺口。

每次调度只提供该环节所需的任务卡、验收标准草案、已知决策和相关材料，不转发全套背景。

## 路由硬规则

先形成任务卡，再进行标杆侦察并填写路由卡。路由卡必须在实际调用前展示或记录；仅记录已选、被触发但跳过、或因缺失而不可用的环节及其事实理由，不为未触发环节逐项填卡。卡片模板均见 `references/cards.md`。

### 1. 任务卡

记录：重复任务、目标用户、典型输入、预期业务产物与 Skill 产物、不可接受结果、复用范围、已有材料、既有版本和本轮需要支持的决定。

**验收标准草案（必填）**：列出预期产物的可观察成功标准与不可接受结果。该草案随交接卡原样传递给评估环节；评估结论必须逐条回引各标准的验证状态，不得以总体印象替代。

关键输入缺失且会改变 Skill 的目标、触发边界、交付物、事实规则或验收标准时，列出工作假设和影响，在可逆范围内先采用最保守、可修改的方案继续；是否暂停按"暂停规则"一节判定。

完成条件：任务卡可使未参与前文的执行者理解本轮要改什么、为什么改、什么算成功。

### 2. 主动标杆侦察

使用者不需要预先知道是否存在合适标杆。总控负责判断是否侦察，并记录结论。

出现任一信号时，必须进行轻量侦察：

- 新建 Skill 且拟跨项目或跨团队复用；
- 任务高风险、复杂，或对质量机制的稳定性要求高；
- 关键设计存在多个合理方案，且现有材料无法支持选择。

侦察首先判断两个方向是否有潜在增益：

| 侦察方向 | 适用问题 | 侦察后动作 |
|---|---|---|
| 技术/产品标杆 | 工作流依赖软件结构、自动化、文件处理、数据模型、开源工具或成熟产品机制 | 有可靠候选时调度 `skill-from-externals` 分支 B；没有可靠候选时记录搜索范围和无结果。 |
| 实践案例标杆 | 工作流依赖人类判断、沟通、研究、创作、服务或行为质量，且真实成功与失败模式会改变规则 | 有足够具体案例线索时调度 `skill-from-masters`；案例不足时记录缺口，不把理论常识伪装为实践规律。 |
| 现成能力复用 | 需要判断已有能力能否复用，避免重复建设 | 调度 `skill-from-externals` 分支 A；先查团队工作区已有 Skill，再查外部生态。 |

侦察不是强制深度学习。发现的来源与本轮问题无关、质量不足、不能合法复用，或现有真实材料已经足以支持局部可逆修订时，可不进入深度学习；但必须说明判断依据和跳过限制。

侦察能力因网络、权限、工具故障或来源不可访问而无法执行时，记录"未执行及原因"。此时仅可基于已有材料推进不依赖标杆结论的局部、可逆候选，不得声称已形成标杆学习结论；若缺少外部证据会影响不可逆操作、广泛推广或版本取舍，按"暂停规则"处理。

各学习环节负责主动搜索和筛选来源，不要求使用者预先指定项目或案例；其发现候选后，遵循对应 Skill 的选择和确认规则。下游确认只约束采用其专属来源或案例结论的动作；未获确认时，该学习环节标记为"未完成"，不阻止推进完全独立、可逆且不引用该结论的候选工作。

仅在实际执行外部侦察时，记录最小证据：侦察方向、一个代表性候选或"无可靠候选"、深入或跳过原因。

完成条件：形成标杆侦察结论，说明是否搜索、发现什么、为何深度调度或不调度、以及跳过造成的限制。

### 3. 路由卡

按 `references/cards.md` 中"路由卡"模板填写，调度粒度为环节。以下条件满足时必须调度对应环节；条件不满足时不得为了形式调用：

| 触发信号 | 必须调度 | 最低专项产出 | 不得替代为 |
|---|---|---|---|
| 需要判断已有能力能否复用 | `skill-from-externals` 分支 A | 候选清单、质量依据、推荐或无结果说明 | 凭记忆推荐或猜测包名 |
| 标杆侦察发现可靠 GitHub 项目，且项目机制能改变本轮设计 | `skill-from-externals` 分支 B | 项目机制、限制、来源归属和不可直接迁移部分 | 只读 README 后直接照搬 |
| 标杆侦察发现足够具体的黄金/失败案例，且案例规律能改变本轮规则 | `skill-from-masters` 案例学习 | 有效/无效对照和可复用规则 | 理论常识或单一案例 |
| 风险集中于触发、分支、指令层级、引用、上下文或完成条件 | `writing-for-agents` 结构审查 | 明确的结构建议及对应问题 | 仅润色措辞 |
| 要新建、更新、安装、校验或打包正式候选 | `skill-creator` 相应环节 | 正式位置、结构校验和安装/更新事实 | 手工复制后宣称已安装 |
| 要判断改动是否值得保留、比较版本、诊断真实任务问题或决定推广 | `skill-effectiveness-evaluator` 相应层级 | 匹配风险级别的测试设计与证据结论 | 结构校验、作者直觉或自评 |

默认顺序为：标杆侦察 -> 发现或学习 -> 指令设计 -> 创建 -> 评估。只有上一阶段的专项产出不改变下一阶段输入时才可并行。

### 4. 改造既有 Skill 的最小路由

既有 Skill 的局部改造先执行"增量演进原则"中的能力基线和演进清单，再至少调度：

1. `skill-creator` 结构校验与安装环节，用于备份核验、正式更新与结构校验；
2. `writing-for-agents` 结构审查，仅当本轮改动涉及触发、流程分支、确认门禁、引用资料、信息层级或完成条件；
3. `skill-effectiveness-evaluator`，当需要判断改动效果、选择版本、判断是否保留或准备推广。

若改动同时命中标杆侦察的任一信号，必须先进行标杆侦察。仅修正错别字、链接、目录路径或不改变行为的格式时，可只调度 `skill-creator`，并记录为"非行为改动"。

行为改动完成后，路由卡补充演进清单（模板见 `references/cards.md`）。

## 调度与交接

本轮仅调度一个参与 Skill 的一个环节时，交接卡可免填；跨两个及以上环节调度时，交接卡必须保留：

- 已知的用户要求与业务规则；
- **验收标准草案（原样传递，不得改写）**；
- 标杆来源和可复用机制；
- 工作假设与限制；
- 未决问题；
- 产物位置与状态：上游产物位置、已写入候选的内容、保留为候选或待验证的内容。

对可逆的候选设计，基于任务材料和来源给出默认方案并继续执行，同时在交接卡中标明假设。模型建议、未反对或未回复只能作为默认方案的依据，不能伪装成用户明确决定。是否暂停按"暂停规则"一节判定。

每阶段结束前检查是否获得该环节的专项产出。没有专项产出时，将其记为"已加载未执行"，不得在结论中计为已完成的专业方法。

## 设计与创建候选

根据任务卡、标杆侦察与路由卡中的默认方案，调度 `skill-creator` 创建或更新候选。

候选有显著分支、引用资料、完成闸门或触发风险时，先调度 `writing-for-agents` 结构审查。来自外部学习或案例学习的内容必须交接"来源、机制、适用边界、不可直接迁移部分"后才能写入候选。

候选保持最小化。未经明确要求和验证，不写入来源专属规则、业务阈值、凭据或机器路径。对既有 Skill 的行为改动，先运行 `scripts/verify_backup.py` 确认备份可读，再更新正式文件。

创建环节的完成条件按顺序为：

1. 运行 `scripts/validate_structure.py` 且通过；
2. **触发边界验证**：准备至少 3 条应触发提示与 2 条近似但不应触发提示，在独立会话或子代理中仅凭候选的 frontmatter description 判断触发结果并记录；全部命中方可通过，未通过先修订 description；无独立会话或子代理能力时，由编排方仅凭 description 文本判断，并如实标注“降级验证，待独立复验”；降级通过时决策建议不得高于“小修后使用”，且不得宣称可推广；
3. 执行"通用轻量架构检查"；发现阻塞性歧义或隐含依赖时先做最小修正；
4. 进入行为验证。

完成条件：候选有唯一正式位置、明确触发与不触发边界、引用资源存在，并留有结构校验脚本输出、触发验证记录及通用轻量架构检查证据。

## 验证与比较

需要判断保留、修改、比较或推广候选时，调度 `skill-effectiveness-evaluator` 的对应层级。

- 探索：核心任务加边界任务，支持首轮信号；
- 标准比较：版本选择或优化决策，采用隔离运行和人工复核；
- 严格审计：高风险、广泛推广或版本归档，满足完整审计门禁后再形成正式结论。

评估环节的输入必须包含任务卡中的验收标准草案；评估结论逐条回引各标准的验证状态。存在旧版本时，基线与候选使用相同输入和验收标准。每次行为改动至少验证两类路径：本轮要修复或新增的路径，以及一个未改动但关键的既有路径。若任一基线路径缺失、弱化或出现行为退化，先归类为版本回退；除非作者明确接受退役，不得以新功能存在为理由忽略回退。最终业务产物质量、过程遵循、环境限制和任务设计问题分别记录。

只有声称"已评估""已回归"或"已独立审查"时，才创建最小证据卡（模板见 `references/cards.md`），并运行 `scripts/check_evidence_card.py` 校验。

没有实际结果或证据位置时，只能写"已完成规则修订，尚未完成行为验证"。不得将静态结构检查、规则阅读、计划中的测试、缓存旧版本预览或作者直觉表述为"已评估""回归通过"或"独立审查完成"。不为轻量改动创建完整实验包。

## 交付前最小化检查

仅当产物将被交付、分享、上传或跨项目复用时执行。交付物只保留受众完成任务所需的信息；移除或不写入开发者身份、内部绝对路径、工具或模型日志、提示词、密钥、内部讨论、无关人员信息和无关敏感业务信息。此检查不要求扫描或留存全部原始材料。

## 作者决策卡

每轮以 `references/cards.md` 中"作者决策卡"模板结束。其中"依据"必须回引验收标准草案各条的验证状态；不超出当前证据宣称广泛有效、已成功安装、平台兼容或适合推广。是否安装、发布、推广或停止由作者决定。

## 暂停规则

发生以下任一情况时暂停相应阶段，说明已完成部分、阻塞、影响和恢复所需的最小作者决定。本节是暂停条件的唯一权威位置，其他章节引用本节：

- 任一核心硬门禁能力尚未确认可用；
- 选定路径所需的材料、来源、案例或任务输入缺失，且保守方案仍会导致覆盖既有内容、不可逆操作或外部系统动作；
- 操作不可逆、影响外部系统或会覆盖已有 Skill，且尚未获明确确认；
- 评估不能区分候选机制、运行环境或任务设计的影响；
- 继续执行只能增加文档或产物，不能增加决策证据。
