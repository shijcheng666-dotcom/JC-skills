# 任务设计原则

## 核心原则

设计测试任务前，先完整了解被测 Skill，而不只看它的 description 或自我介绍。至少阅读：

- `SKILL.md` 的目标、触发条件、流程和输出要求；
- 它引用的 references、模板和脚本；
- 关键工具依赖、确认门槛、失败路径和状态规则；
- 内容结构中可能实际影响行为的约束、优先级和例外。

据此识别 Skill 的真实目标：它试图改善什么任务结果、可靠性、效率、用户成本或风险控制。任务应围绕这个目标设计，而不是围绕 Skill 是否复述自身流程来设计。

## 任务覆盖

根据 Skill 的目标设计典型核心任务，观察它是否真的带来预期收益。

同时阅读 Skill 的薄弱点、复杂规则、关键依赖和容易误解的部分，设计适量边界或压力任务，观察它是否会：

- 在时间线、数字、冲突材料或不完整信息下出错；
- 过度外推、遗漏关键限制或混淆事实与假设；
- 在简单任务、模糊需求或不应触发的场景中增加不必要成本；
- 错误处理确认、澄清、拒绝、降级或失败路径；
- 因复杂流程、模板或工具依赖产生副作用。

如果不同版本的具体内容或架构存在明显差异，再设计针对该差异的任务，验证差异是否实际改善了用户收益、可靠性或成本。不得把“是否执行某个流程”本身直接当成成功标准。

## 基本公平性

所有候选使用相同的用户输入、材料、确认消息、工具条件和执行约束。不要把成功标准、预期结果、评分卡、其他候选信息或版本差异提示泄露给任务执行子代理。

任务应足以观察目标差异，但不要设计成只有篇幅、格式复杂度或流程名称能够区分候选。没有唯一答案时，按可接受结果范围和不可接受错误评价，不强行规定唯一写法。

快速探索只需选择一个核心任务和一个边界或压力任务；标准比较和严格审计根据 Skill 目标、薄弱点和版本差异适当增加任务。样本不足时降低结论强度，不把任务设计上的观察直接归因于 Skill。
