# Skill Creator

本技能用于指导创建高质量、可复用的 skill。

## 调度接口

**编排入口**：在 skill-orchestrator 编排的生产流程中，由 orchestrator 显式调度。轻量或个人 Skill 的创建任务中，本技能按下方完整流程自主执行；被编排调度时只执行下表指定环节，不自行扩展为完整流程。

| 环节 | 何时被调度 | 需要输入 | 专项产出 | 完成条件 |
| --- | --- | --- | --- | --- |
| 创建与起草 | 需求与标杆结论已确认，需从零起草候选 Skill | 任务卡摘要、验收标准草案、标杆侦察结论 | 候选目录（SKILL.md + 资源文件） | 候选结构自检通过；所有引用资源真实存在 |
| 结构校验与安装 | 候选已定稿，需校验并落到正式位置 | 候选目录、目标范围（全局、工作区或候选暂存目录） | 校验通过事实、正式位置、加载状态声明 | 校验脚本退出码为 0；加载状态如实声明（见步骤 5） |
| 打包分发 | 明确要求导出、分享或分发 | 候选目录、输出目录（可空） | 分发包路径与校验结果 | `package_skill.py` 校验通过 |

被调度时，若任务与以上环节均不匹配，记录状态缺口并返回，不得将本技能整体替代执行。

## 关于 Skill

Skill 是模块化、自包含的能力包，用来扩展 智能助手 的专业能力。它可以提供特定领域知识、稳定工作流、工具调用方法和可复用资源，让通用代理在某类任务上表现得像专门代理。

### Skill 提供什么

1. 专业工作流：特定领域的多步骤流程。
2. 工具集成：处理特定文件格式、API 或平台的说明。
3. 领域知识：公司内部知识、数据 schema、业务逻辑。
4. 打包资源：脚本、参考文档、模板和素材。

### Skill 结构

每个 skill 都包含一个必需的 `SKILL.md`，以及可选的资源目录：

```text
skill-name/
├── SKILL.md
│   ├── YAML frontmatter metadata
│   │   ├── name:
│   │   └── description:
│   └── Markdown instructions
└── Bundled Resources
    ├── scripts/
    ├── references/
    └── assets/
```

#### SKILL.md

元数据质量：YAML frontmatter 中的 `name` 和 `description` 决定 智能助手 何时使用该 skill。描述要具体说明 skill 做什么、什么时候使用。建议使用第三人称中文描述，例如“当用户需要……时使用”。

Agent 创建标记：在 Aime 环境中，YAML frontmatter 必须包含 `agent_created: true`，这样后续 `skill_manage` 才能修改或删除该 skill；其他环境按平台要求决定。

版本标识：独立分发的 Skill 在 frontmatter 中记录 `version`，首个候选从 `0.1.0` 开始，后续按步骤 4 的规则递增；已有其他版本序列保持连续。

#### 打包资源

##### Scripts (`scripts/`)

适合放可执行代码，例如 Python、Bash 脚本。用于需要确定性、重复执行或不适合反复手写的任务。

- 何时包含：相同代码会被反复重写，或需要确定性可靠性。
- 示例：`scripts/rotate_pdf.py` 用于旋转 PDF。
- 好处：节省 token、行为稳定，可在不读入上下文的情况下执行。
- 注意：如果需要修补脚本或适配环境，智能助手 仍可能读取脚本内容。

##### References (`references/`)

适合放按需加载的参考资料，用来支持 智能助手 的判断和执行。

- 何时包含：智能助手 工作时需要参考文档。
- 示例：`references/finance.md`、`references/policies.md`、`references/api_docs.md`。
- 适用：数据库 schema、API 文档、领域知识、公司制度、详细流程说明。
- 好处：保持 `SKILL.md` 精简，只在需要时加载。
- 最佳实践：大文件超过 10k 词时，在 `SKILL.md` 中写明建议搜索关键词。
- 避免重复：同一信息放在 `SKILL.md` 或 references 文件之一即可。核心流程放 `SKILL.md`，详细资料放 references。

##### Assets (`assets/`)

适合放输出时会使用的文件，不是为了读入上下文。

- 何时包含：最终输出需要模板、图片、图标、字体或样例文件。
- 示例：`assets/logo.png`、`assets/slides.pptx`、`assets/frontend-template/`、`assets/font.ttf`。
- 适用：模板、图片、图标、样板代码、字体、样本文档。
- 好处：把输出资源与说明文档分离。

### 渐进式加载原则

Skill 使用三层加载来节省上下文：

1. 元数据（`name` + `description`）：始终可见。
2. `SKILL.md` 正文：skill 被触发时加载。
3. 打包资源：智能助手 判断需要时再加载。

## Skill 创建流程

按顺序执行以下流程。只有在明确不适用时才跳过某一步。

### 步骤 1：用具体例子理解 skill

只有在使用场景已经非常清楚时才跳过此步骤。即使是更新已有 skill，也建议先确认例子。

创建有效 skill 前，先理解它将如何被使用。例子可以来自用户，也可以由你提出并请用户确认。

例如创建 `image-editor` skill 时，可问：

- 这个 skill 要支持哪些功能？编辑、旋转、去红眼，还是更多？
- 能给几个实际使用例子吗？
- 用户会怎样描述一个应该触发该 skill 的请求？

不要一次问太多问题。先问最关键的问题，再根据回答追问。

当已经清楚 skill 应支持的能力边界时，结束此步骤。

### 步骤 2：规划可复用内容

先做最小复用检查：快速确认是否已有现成方案——检索当前工作区技能目录，以及该任务领域的常见开源工具或生态（轻量任务做一次快速检索即可）。已有可靠现成方案时优先复用或在其基础上改造，并把结论一句话告知用户；没有时再继续下面的规划。

把具体例子转成可复用 skill 内容：

1. 分析如果从零完成该例子需要哪些步骤。
2. 找出重复任务中有价值的 `scripts/`、`references/`、`assets/`。

示例：`pdf-editor` skill 处理“帮我旋转这个 PDF”时，旋转 PDF 需要反复写相同代码，因此应放入 `scripts/rotate_pdf.py`。

示例：`frontend-webapp-builder` skill 处理“做一个 todo app”时，前端样板工程可放在 `assets/hello-world/`。

示例：`big-query` skill 处理“今天有多少用户登录”时，表结构关系需要反复查询，因此应放入 `references/schema.md`。

最终产出一份资源清单：需要哪些脚本、参考文档和素材。

### 步骤 3：初始化 skill

当 skill 需要从零创建时，先确定唯一的规范名称、作用域和正式目录。如果 skill 已存在，只是继续迭代或打包，可以跳过创建步骤。

**环境探测（先执行）**：本步骤的路径与安装规则按当前环境分两种模式。

- **Aime 模式**：当前环境提供 `create_skill` 工具时，按下方“Aime 专属规则”执行（唯一入口、路径约定、`loaded: true` 验证）。
- **通用模式**：当前环境没有 `create_skill` 工具时，技能目录按实际约定探测——优先检查目标工作区现有的技能目录（如 `.trae/skills/`、`.aime/skills/` 或工作区内的 `skills/`），探测不到时询问用户安装位置；安装降级为直接创建文件，并在完成时如实声明“未经平台安装流程，技能加载与发现状态未验证”。编排流程中的候选通常先落在候选暂存目录（非正式技能目录）；暂存只视为存放与校验，不视为安装，待编排流程决定交付时再移入正式技能目录。

两种模式下，名称规范化、唯一目录、步骤 1/2/4/6/7 的要求相同。

**Aime 专属规则**（仅 Aime 模式适用）：

skill 可放在两个位置：

| Type | Path | Scope |
|------|------|-------|
| User skill | `config/aime/skills/skill-name/`（相对于桌面应用用户数据目录） | 所有项目可用 |
| Project skill | `.aime/skills/skill-name/` | 当前仓库协作者共享 |

安装位置是必选信息。用户没有明确指定全局或工作空间时，必须先询问用户选择：

- **全局**：使用相对路径 `config/aime/skills/skill-name/`（相对于桌面应用用户数据目录），对所有项目可用。
- **工作空间**：使用相对路径 `<当前项目>/.aime/skills/skill-name/`，仅当前项目可用。

在用户明确选择前，不得创建目录、写入文件或调用 `create_skill`，也不得自行猜测默认范围。用户选择后，严格按对应范围执行；不要在说明或实现中写入 Aime 全局配置目录的绝对路径。

跨平台解析全局路径时，使用当前系统的桌面应用用户数据目录：Windows 通常以 `%APPDATA%/ai.aime.desktop.dev` 为根，macOS 通常以 `~/Library/Application Support/ai.aime.desktop.dev` 为根；两者都追加相对路径 `config/aime/skills/`。文档中的路径统一使用 `/`，实际文件操作由系统路径工具转换分隔符。

一次用户创建请求只能产生一个正式 skill 目录。在任何写文件、初始化或调用工具之前，先把用户提供的名称规范化为小写字母、数字和短横线组成的唯一内部名称；目录名、frontmatter `name` 和 `create_skill.name` 必须始终使用这个名称，不得先用中文名或临时名称创建一份，再用规范名称创建另一份。

`create_skill` 是 Aime 模式下唯一允许创建正式 skill 目录的入口。准备好最终的 `name`、`description` 和 `SKILL.md` 正文后，只调用一次 `create_skill`，由工具解析正确的 Aime 配置目录并刷新技能发现。仅在用户明确选择后传入对应的 `scope`：全局使用 `scope: "global"`，工作空间使用 `scope: "workspace"`。未选择时不得调用 `create_skill`。

禁止在调用 `create_skill` 前后，通过 `Copy-Item`、`cp`、文件写入或其他命令手工创建、复制或重命名 Aime 全局或项目的正式 skill 目录。只要已经手工写入或复制到正式目录，就不得再次调用 `create_skill`；应停止并复用或清理同一个目录，而不是创建第二份。

只有工具返回 `loaded: true`，才能向用户说明技能已安装、已进入技能发现列表并可直接使用。工具报错或返回未加载状态时，必须如实说明未安装成功，不得仅凭文件生成、目录创建或打包成功宣称“已安装”。

instruction-only skill 不需要运行初始化或打包脚本。需要搭建 `scripts/`、`references/` 或 `assets/` 的复杂 skill 时，可以在非正式技能目录中运行 `init_skill.py` 生成临时结构：

```bash
python scripts/init_skill.py <skill-name> --path <output-directory>
```

必须显式传入 `--path`，并使用前面确定的同一个规范名称。临时目录不得位于正式 `skills` 目录内。`init_skill.py` 只负责准备内容，不能安装 skill，也不能替代平台安装和发现验证。

脚本会：

- 创建 skill 目录。
- 生成带 frontmatter 和 TODO 占位的 `SKILL.md`。
- 创建示例资源目录：`scripts/`、`references/`、`assets/`。
- 添加可自定义或删除的示例文件。

初始化后，按实际需求修改或删除生成的 `SKILL.md` 和示例文件。Aime 模式下，调用一次 `create_skill` 写入最终 `SKILL.md` 后，只把实际需要的 `scripts/`、`references/`、`assets/` 放入 `metadata.file` 所在的同一个目录；禁止把临时 skill 根目录或临时 `SKILL.md` 复制到正式技能目录，也不得再次调用 `create_skill`。通用模式下，将最终文件直接写入探测确定的技能目录。

### 步骤 4：编辑 skill

编辑 skill 时，要记住它是给另一个 智能助手 实例使用的。重点写入对 智能助手 真有帮助、且不显而易见的信息，例如流程经验、领域细节、可复用脚本和模板。

#### 先处理可复用资源

从前面识别出的 `scripts/`、`references/`、`assets/` 开始实现。某些资源可能需要用户提供，例如品牌素材、模板、内部文档。

删除不需要的示例文件和目录。初始化脚本创建的示例只是展示结构，大多数 skill 不需要全部保留。

#### 更新 SKILL.md

写作风格：整份 skill 使用指令式、客观说明的中文，不写成第二人称聊天。优先写“执行 X 时，先做 Y”，不要写“你应该……”

完成 `SKILL.md` 时回答三个问题：

1. skill 的目的是什么？
2. 什么时候应该使用该 skill？
3. 智能助手 实际应该怎样使用它？所有可复用资源都要被引用到。

#### 迭代变更集与版本基线

更新已有 Skill 时，先记录当前版本和本轮变更集，再开始修改。每个独立分发的 Skill 维护独立于 skillfactory 套件的版本历史。

- **变更集与分层验收**：同一行为目标、可共同验收且需共同回滚的修改归为一组；可独立验收或回滚、业务口径不同的修改拆开，行为修改与纯结构整理分开。每个原子问题完成即检查，变更集完成后用同一批用例统一评估，发布前执行关键路径回归与打包检查；无需用户为每个原子问题重复决策。
- **可选 Git 协同**：Git 可用且作者同意时，先记录工作区状态与基线提交或标签。提交只作为有意义的检查点，作者接受后再固化正式版本和标签；不自动提交、推送或发布。只有并行或高风险试验才需要分支，普通顺序迭代不强制分支。
- **无 Git 降级**：Git 不可用或作者不采用时，在 Skill 源目录外保存快照、版本号、变更摘要和文件哈希，并声明差异审查与回滚能力的限制。快照与备份不得放在 Skill 源目录内；版本库元数据、快照、备份和缓存不得进入分发包。
- **版本递增**：已有版本序列保持连续；新采用版本管理的 Skill 默认使用语义化版本。PATCH 用于不改变使用方式的修复，MINOR 用于向后兼容的新能力，MAJOR 用于触发、输入输出或使用契约的不兼容变化；MAJOR 和业务口径变化须由作者确认。
- **验收后冻结**：候选验收后发生实质修改，原评估结论即失效，至少重跑受影响用例和关键回归。只有最终接受版本才能形成正式版本与分发包；评估证据保存在 Skill 源目录之外的过程记录中，真实案例入库前须脱敏。

### 步骤 5：安装并验证

**Aime 模式**：除非用户明确只要求生成或打包文件，否则创建任务必须通过唯一一次 `create_skill` 调用完成正式目录创建和安装。调用成功后，根据返回结果核对：

1. `metadata.file` 指向当前 Aime 实例的全局或项目技能目录。
2. `metadata.loaded` 为 `true`。
3. 输出明确包含技能发现已刷新。

任一条件不满足时，不得宣称技能已经安装或可以直接使用。不要用手写其他产品的 skill 目录、运行打包脚本或生成压缩包替代此步骤。不得为了修正名称、补资源或验证发现，再创建另一个名称或另一个正式目录；应继续操作 `metadata.file` 指向的唯一目录。

**通用模式**：将最终 `SKILL.md` 与资源写入探测确定的技能目录，运行 `scripts/quick_validate.py` 校验，然后如实声明三项事实：文件已就位的位置、结构校验结果、“加载状态未验证（当前环境无平台安装工具）”。不得仅凭文件生成或校验通过宣称“已安装可用”。

### 步骤 6：按需打包 skill

只有用户明确要求导出、分享或分发时，才把已完成的 skill 打包成 zip。`.zip` 或 `.skill` 文件只是分发包，不代表已经安装。打包前确认待打包目录与最终接受版本一致；验收后又有实质修改时，先按步骤 4 重验。输出目录应位于 Skill 源目录之外，版本库、备份和缓存不得进入分发包。确认正式技能目录或目标工作区的写入权限，不要为了打包覆盖已安装目录。打包脚本会先自动校验：

```bash
python scripts/package_skill.py <path/to/skill-folder>
```

可指定输出目录：

```bash
python scripts/package_skill.py <path/to/skill-folder> ./dist
```

打包脚本会：

1. 校验：
   - YAML frontmatter 格式和必填字段。
   - skill 命名规范和目录结构。
   - description 的完整性和质量。
   - 文件组织和资源引用。

2. 打包：
   - 校验通过后创建以 skill 命名的 zip，例如 `my-skill.zip`。
   - 保留正确目录结构，方便分发。

如果校验失败，脚本会报告错误并停止。修复后重新运行打包命令。

### 步骤 7：测试、评估与迭代

用户测试 skill 后，基于真实使用反馈迭代。对于输出可客观判断的 skill（文件转换、数据提取、代码生成、固定工作流），先设计 2-3 个真实测试案例；对于主观创作类 skill，以用户定性反馈为主，不强行设置形式化断言。

评估时优先保留两类对照：

- 新建 skill：无 skill 的基线。
- 更新已有 skill：修改前的快照作为旧版本基线。

每个测试案例至少记录：输入提示、期望结果、实际输出、耗时或资源消耗（若可获得）、通过/未通过依据和用户反馈。基线与新版本应使用相同提示、相同输入和相同验收标准，避免把环境差异误判为 skill 改进。

当有可用的独立执行能力时，优先并行运行“带 skill”和“基线”两组；运行期间先拟定客观检查项，再汇总通过率、耗时和 token 等指标。若有多个版本，保持版本顺序清晰，并补充定性分析，识别不区分版本的检查项、高方差案例和质量与成本之间的权衡。

如果有评测查看器，使用现成查看器让用户同时查看各版本输出和量化结果；没有查看器时，直接在对话中逐案例呈现结果并请求反馈。不要为了形式化评测而阻塞简单 skill 的交付。

迭代流程：

1. 在真实任务中使用 skill。
2. 观察卡点、低效之处和未触发场景。
3. 判断应更新 `SKILL.md`、frontmatter 描述，还是打包资源。
4. 实施最小、可泛化的修改，避免针对单个案例过拟合。
5. 用同一测试集重跑并与旧版本或无 skill 基线比较。
6. 用户确认满意、反馈为空，或已无法获得有意义的改进时停止。

### 技能描述优化

frontmatter 中的 `description` 是触发 skill 的主要依据。完成创建或更新后，视情况检查描述是否覆盖：技能做什么、何时使用、典型表达和边界场景。复杂 skill 可准备一组真实的“应触发”和“近似但不应触发”提示进行抽样验证；不要只用关键词命中判断，也不要把所有场景都写成宽泛的强制触发。
