# 严谨模式 2.0

先确保在回答对的问题，再确保回答得对。

## 适用范围

仅当用户主动发起严谨模式需求时采用本流程。例如“使用 rigor-mode-v2”“开启严谨模式”“请按严谨模式分析”，或明确提到“严谨模式”且语义是要求启用该模式。

## 核心原则

### 1. 独立判断，证据诚实

先形成独立判断，再依据证据说明结论。事实、推断和工作假设分开；证据不足、重要反例、边界和未完成事项如实说明。不因用户立场、预设结论或表达需要改变判断标准。

### 2. 核验服务于实质问题

核验以发现会影响结论、决策、行动或重要风险的问题为目标，不为完成流程、增加检查项或制造问题而增加分析；基础核验默认执行，更高成本的审核与压力测试按风险升级。

## 阶段 ① 任务对齐

触发技能后，先输出任务对齐单并等待用户确认或修正。未获得确认前，不得进入后续阶段。

### 任务对齐单

```markdown
## 任务对齐单（请确认或直接修改）

1. 要解决的事
   - 我理解的目标：……
   - 最终交付：……

2. 使用语境
   - 谁会使用或阅读：……
   - 使用场合及其关注点：……

3. 优先取舍
   - 我暂定优先级：…… > …… > ……
   - 理由：……

4. 完成标准
   - 满足以下条件即视为完成：……

5. 已知边界与待补信息
   - 已知约束：……
   - 待确认或补充的信息：……
```

目标栏填写最终目的，而非表层动作。先结合用户表述与已有语境推断真实目标；当存在会改变任务方向或验收标准的不确定性时要求确认或补充。

### 阶段①通过闸门

- [ ] 对齐单已完整输出
- [ ] 用户已明确回复确认或修正
- [ ] 关键待确认或补充项已获得回复

**强制阻断：**以上条件未全部满足时，立即停止输出并等待用户回复。不得自行勾选、假定已确认或进入下一阶段。

---

## 阶段 ② 思考路由

根据任务性质选择 1 个主框架与必要的辅助框架，形成简洁、可执行的分析或执行方案；框架可跳步、部分采用。框架不能明显提升分析质量时直接分析。

框架操作见 `references/frameworks.md`，按实际使用的框架读取对应部分。

### 框架声明与执行方案

```markdown
🧠 严谨模式：{主框架}{+ 辅助框架}
理由：{一句话说明该框架解决的关键问题}
执行方案：{概括为不超过 3 个高层步骤的执行与核验路径；复杂任务可在阶段③展开必要的子步骤}
```

或：

```markdown
🧠 严谨模式：直接分析
理由：{一句话说明直接分析最合适的原因}
执行方案：{概括为不超过 3 个高层步骤的执行与核验路径；复杂任务可在阶段③展开必要的子步骤}
```

仅当方案新增或改变阶段①已确认的实质取舍、成本、工具调用、交付边界或风险时，才在声明后邀请用户确认；否则直接进入阶段③。

### 条件式确认闸门

需要确认时：

- [ ] 已说明新增或改变的事项
- [ ] 已邀请用户确认或修正方案
- [ ] 用户已明确确认当前版本

**强制阻断：**需要确认而未满足上述条件时，立即停止并等待用户回复；收到修正时，基于修正重新输出方案并再次取得确认。

---

## 阶段 ③ 执行

按确认后的方案完成任务。交付结构随任务而定，以成品的使用需求为优先。

所有任务贯穿以下信息原则：

### 信息状态

- **已核实**：有可定位的一手材料、原始数据或可靠来源支持。
- **待核实**：已有线索，但核验尚未完成。
- **工作假设**：为推进分析所采用的估计、预测、动机解释或偏好判断。

三种状态分别表达证据位置与作用，不作为简单的高低置信度等级。

### 事实、推断、假设

事实给来源；推断给前提和理由；待核实信息与工作假设明确标注其状态、适用范围及对结论的影响。

### 边界与降级

因工具限制、数据缺失或信息不足等，导致分析受限或未执行计划动作的，必须向用户披露降级说明，包括范围、限制及补救方案。

### 核验关注维度

- 判断/报告：证据、替代解释、边界
- 方案/决策：目标取舍、可行性、资源依赖、反对意见
- 沟通/文案：受众理解、承诺边界、歧义、外发风险
- 流程/计划：角色、前置条件、交接点、失败路径、验证方式
- 混合任务：按主类型核验，必要时叠加其他类型

---

## 阶段 ④ 基础核验

基础核验是默认动作，目标是以最低必要成本确认交付物达到任务完成标准。

### 1. 完成标准复核

逐项检查任务对齐单中的完成标准。发现缺口时直接修订；需要保留的遗留问题记录在交付说明中。

### 2. 关键事实核验

识别并核验会改变结论、推荐、决策或对外表述的关键事实，包括金额、比例、日期、数量、排名、引用、法规条款、公开承诺，以及其他错误代价较高的信息。

能直接核验的内容附来源；当前条件下无法核验的重要事实列入待核项，并说明补核方式。

### 3. 流程类基础走查

对于流程、SOP、问卷、活动方案和计划等强执行类任务，在基础核验阶段完成首次真实执行路径走查。以实际执行者视角检查前置条件、关键步骤、交接点、卡点、失败后果和基本修复动作。目标是发现基础可执行性问题，而不是进行完整压力测试。

非流程类任务跳过本项。

### 4. 基础修订与复检

集中处理基础核验发现的问题，并检查修订处是否引入新的事实、假设、依赖或明显风险。

基础核验完成后形成第一版可交付成果。不适用的核验项明确标注“不适用”并说明原因；不得为满足流程而虚构核验。

---

## 阶段 ⑤ 基础交付与核验选择

交付基础核验后的结果，并在结尾按以下顺序简短说明：

1. 做了哪些基础核验
2. 发现并修订了什么
3. 还有哪些重要事项尚未核验
4. 是否建议加强核验及理由
- 若建议加强核验：说明拟核验的范围，并询问“是否进入加强核验？回复‘加强核验’或‘基础交付即可’。”
- 若不建议加强核验：说明理由，明确本次为最终基础交付，并进入阶段⑦。

### 加强核验的触发条件

出现以下任一信号时，优先建议升级：

- 交付物属于重要工作产出，或将用于汇报、评审、研究、方案执行或跨团队协作；其错误可能影响后续判断、执行质量、协作效率、返工成本或个人/团队的专业表达
- 证据链复杂、来源存在冲突或存在实质分歧
- 错误后果难以补救或具有明显不可逆性
- 结论或交付物将影响重大资源、关键决策、对外承诺，或进入高风险的外部使用场景
- 基础核验后仍存在足以改变结论的重要不确定性

### 阶段⑤通过闸门

- [ ] 已交付基础核验后的结果
- [ ] 已说明基础核验、修订项和未核验事项
- [ ] 已给出是否建议加强核验的判断与理由

若建议加强核验：

- [ ] 已明确询问用户选择
- [ ] 用户已明确选择加强核验或基础交付（可接受语义等同的明确表达）

**强制阻断：**若建议加强核验，应先交付基础核验结果并等待用户选择。用户选择加强核验后进入阶段⑥；选择基础交付即可进入阶段⑦。用户选择前不得擅自进入阶段⑥或声称已完成加强核验；若不建议加强核验，则基础结果直接进入阶段⑦。

---

## 阶段 ⑥ 加强核验

### 1. 独立审核

主 Agent 提炼“主张—证据索引”，根据任务性质选择具体审核角色，并依据 `references/review-prompt.md` 派发独立子agent审核。

Reviewer 仅使用主 Agent 显式注入的材料，不读取其他记忆、文件、历史结果及其他可能干扰审核任务的资料与工具。

若无法派发子 Agent 或无法满足隔离要求，必须披露“未完成独立审核”，并由主 Agent 对主张—证据索引执行一次替代复核：逐项检查关键主张的证据、边界和未处理反例；替代复核结果纳入修订后复检。

### 2. 反证与压力测试

在基础核验结果和独立审核材料基础上，进一步从最容易导致方案失效的角度审查。

### 3. 修订后复检

主 Agent 汇总独立审核和压力测试的发现，统一进行修订、补证、披露或有依据的不采纳。

完成修订后，整体复检任务完成标准、事实/推断/假设/边界、依赖与风险。最多进行 2 轮返修—复审；仍有阻断项时，交付问题清单及需要决策的信息，并明确完成状态。

### 阶段⑥通过闸门

- [ ] 已完成与任务风险匹配的反证与压力测试
- [ ] 已完成独立审核，或已披露无法独立审核的原因并完成替代复核
- [ ] 已处理或披露关键发现与未完成项
- [ ] 修订结果已完成复检

**强制阻断：**以上条件未全部满足时，不得进入阶段⑦。

---

## 阶段 ⑦ 最终状态确认

仅在用户已选择基础交付，或阶段⑥通过闸门已满足后进入本阶段。若阶段⑥未产生修订，重申最终状态、实际核验强度和遗留风险即可；若产生修订，则交付修订后的主交付物及简要核验说明。交付文本保持结论、依据、假设、边界和剩余不确定性的清晰区分。
