# 严谨模式

把"认真做"变成可检查的流程。按 **任务对齐 → 执行 → 核验与修订 → 交付** 四个阶段推进，顺序不可跳。

适用：需要处理复杂信息、形成重要结论、开展研究分析、进行方案决策或完成关键写作的场景——任务通常存在隐含目标、证据缺口、立场冲突、协作依赖或执行风险，用户希望得到经得起追问的产物。

不适用：闲聊、灵感发散、简单改写、快速草稿或可低成本纠错的任务，用户明确只需要快速初稿的场景。

原则字典在 `references/principles.md`。执行到哪个阶段，读取标有该阶段或【贯穿】标记的条目；不要一次加载全部内容。

---

## 阶段 ① 任务对齐

开工前，基于用户的原始输入预填一页「任务对齐单」。不要把空白表格交给用户填写；只把会改变任务方向、范围、验收标准或证据要求的问题列为待确认项。

```markdown
## 任务对齐单（请确认或直接修改）

1. 要解决的事
   - 我理解的目标：……
   - 最终交付：……

2. 使用语境
   - 谁会使用或阅读：……
   - 使用场合及其关注点：……

3. 优先取舍
   - 我暂定优先级：…… > …… > ……
   - 理由：……

4. 完成标准
   - 满足以下条件即视为完成：……

5. 已知边界与待补信息
   - 已知约束、禁忌或不可触碰项：……
   - 会影响结论、目前仍缺的信息：……

6. 核验强度
   - 我的建议：基础 / 加强
   - 理由：……
```

规则：

- 用户可以一句"按此执行"确认，也可以逐项修改（包括核验强度）；不要要求格式化回复。
- 用户未确认或未修正前，不进入实质产出。可以继续补充、澄清和完善任务对齐单。
- 不要默认追问截止时间。只有时点会改变事实、交付深度、范围、核验强度或行动排期时，才将时间写入第 5 项。
- 不要提问不影响方向的背景信息；不要用"我先给一版再说"替代必要的对齐。

### 核验强度的判断标准

**建议加强**（独立审核 + 反证与压力测试）当满足任一条：

- 对外发布或外发，内容会离开用户个人控制；
- 直接影响关键决策、资源投入、金额、承诺或关系判断；
- 结论依赖复杂证据链、多重假设，或存在明显的利益冲突与立场分歧；
- 错误后果难以逆转或纠正成本高。

**建议基础**（自检 + 关键事实核验）当全部成立：

- 仅内部或个人使用，且可后续修改；
- 不涉及对外表述、不可逆动作或关键决策；
- 证据需求简单，或可由用户快速判断。

建议基础时，必须能逐条排除上述四条"建议加强"的触发条件；无法排除的，按加强建议。

用户在对齐阶段降为基础后，执行中触发升级条件时，停下说明情况并建议升级；用户明确拒绝升级的，继续执行，但交付时必须在核验摘要中披露"曾建议加强核验，用户选择基础"。

## 阶段 ② 执行

严谨不是展示冗长的思考过程，而是让结论、依据、假设和限制可以检查。形成实际交付物时，按以下结构组织实质输出。

```markdown
### 结论与产出
（直接给方案、报告、文案、判断或行动建议）

### 判断依据
- [已核实] 主张：……；依据或来源：……
- [待核实] 信息：……；现有线索及需要补核的原因：……
- [工作假设] 判断：……；前提与理由：……

### 关键假设与可能变化
- 假设：……
- 若该假设不成立：结论或方案中需要调整的部分是……

### 范围与待核验项
- 已覆盖：……
- 未覆盖或受限：……
- 需要核验：……；建议核验方式：……
```

规则：

- 不要求、不展示详细逐步推理过程。
- 已核实、待核实和工作假设必须分开。不得把待核实信息或工作假设写成确定事实。
- 每一条关键推断必须说明前提和理由；每一条已核实的关键主张必须给出可定位的来源或材料。
- 只有用户明确要求方法说明时，提供简短的"分析方法与关键判断点"；不要复述内部逐步推理。
- 若文件、数据、工具或时间限制导致工作降级，必须在"范围与待核验项"中说明已检查、粗略判断和未检查的部分。

### 跨任务判断规则

按交付物性质调整核验重点，不要用岗位或固定任务卡限制理解：

- 判断或报告：重点核查证据、解释边界和替代解释。
- 方案或决策建议：重点核查目标取舍、可行性、资源依赖和反对意见。
- 沟通或文案：重点核查受众理解、承诺边界、歧义、事实与外发风险。
- 流程或计划：重点核查角色、前置条件、交接点、失败路径与验证方式。

### 中途升级触发

执行中如果出现以下任一信号，停下并建议用户将核验强度升级为加强；用户同意后继续：

- 发现结论依赖的证据链明显比预期复杂，或关键假设无法闭合；
- 交付物从个人/内部用途变为对外发布或关键决策依据；
- 执行中暴露重大利益冲突、立场分歧或不可逆后果。

## 阶段 ③ 核验与修订

所有任务都必须完成：**自检、关键事实核验、核验摘要**。核验强度为**加强**的任务，额外完成：**独立审核、反证与压力测试**。流程、SOP、问卷、活动方案或计划类任务，无论核验强度如何都必须做模拟走查。

### 1. 对照任务对齐单自检

逐条对照阶段①第 4 项"完成标准"，列出每条的通过状态、证据或未通过原因。未通过的标准必须返修、取得用户豁免，或作为遗留风险披露。

### 2. 关键事实核验

无论核验强度如何，交付前必须完成：从交付物中提取所有金额、比例、日期、数量、排名、引用原话、法规/政策/条款、公开承诺、涉及个人或组织的事实，以及会改变推荐、资源投入、对外传播或关键决策的外部信息，形成"发送/决策前必核项"清单。能自行核验的，标注已核实及来源；不能核验的，标注待核实并说明补核方式。

### 3. 独立审核（仅核验强度 = 加强时执行）

派一个没有参与制作的子 agent 冷读交付物。作者自检无法替代独立审核。

若当前环境无法派发独立子 agent，必须暂停严谨模式的最终交付，明确告诉用户"独立审核未完成"的限制；可以交付明确标注为"未完成独立审核"的工作版本，但不得称为已完成的加强核验产物。

派发前完成两件事，不写入主交付物：

1. **构造审核角色**：根据任务对齐单和交付物性质，选择最能发现关键错误的人。角色必须具体，不能泛称"资深专家"。
   - 研究或结论：能检查证据、口径与过度外推的审稿人。
   - 方案或决策：会承担执行后果、能指出资源与激励冲突的利益相关方。
   - 沟通或文案：目标受众或负责外发风险的人。
   - 流程或计划：实际执行流程的一线角色。
2. **准备审核材料**：附上用户原始需求和背景原文、任务对齐单、主张—证据索引、待核查交付物。不要附主 agent 的详细推理过程，也不要把用户原始输入改写成作者解读。

使用以下 prompt 派发审核；替换花括号中的内容：

```text
你的角色：{审核角色}

以下是一份你完全没有参与制作的交付物。以该角色的专业视角，核查它是否足以支撑任务对齐单所定义的目标和验收标准。重点查关键主张、关键设计和关键遗漏；不要逐句挑错，也不要为找到问题而制造问题。

## 用户原始需求与背景
{用户原始输入，原文照搬}

## 任务对齐单
{任务对齐单原文}

## 主张—证据索引
{关键主张、对应证据/来源、证据状态}

## 待核查交付物
{交付物全文；不含主 agent 的详细推理过程}

## 核查规则
- 关键主张或关键设计：一旦错误，会改变核心结论、资源投入、对外表述、行动选择或重要关系判断的内容。
- 关键遗漏：验收标准要求、重大边界、必要前置条件、可预见反对意见或证据缺口中，交付物没有处理的内容。
- 审核结论只能使用：支持 / 证据不足 / 存在冲突 / 不适用。
- 严重度只能使用：阻断 / 重要 / 一般。
  - 阻断：事实冲突、关键边界遗漏，或会导致错误行动、明显误导的内容；必须修订。
  - 重要：证据不足、替代解释未处理、执行条件不清；必须修订，或在交付中明确披露为遗留风险。
  - 一般：表达、次要完整性或可优化点；可修订，不阻断交付。
- 证据不足时如实标"证据不足"，不得因没有发现问题就写"支持"。

## 输出格式
| # | 关键主张 / 关键设计 / 关键遗漏 | 审核结论 | 严重度 | 证据或逻辑问题 | 建议处置 |
|---|---|---|---|---|---|
| 1 | ... | 支持/证据不足/存在冲突/不适用 | 阻断/重要/一般 | ... | 补证/修订/披露/保留 |
```

收到报告后，逐条记录处置：

- 采纳：修订交付物。
- 部分采纳：修订对应部分，并说明保留范围。
- 不采纳：说明审核判断为何不成立，并提供依据。

独立审核通过标准：**无"阻断"项；所有"重要"项均已修订、披露为遗留风险，或有明确且有依据的不采纳理由。**

### 4. 反证与压力测试（仅核验强度 = 加强时执行）

目的不是制造负面评价，而是寻找足以推翻、显著削弱或阻断交付物的反例。

从最可能导致交付物失效的角度审查：

- 哪些前提若不成立，会推翻核心结论？
- 哪个利益相关方最可能提出有力反对？其论据是什么？
- 在真实执行中，最可能在哪个条件、资源或协作节点失败？

规则：

- 只列实质问题：能改变决策、影响可行性、损害可信度或需要补证的问题。
- 发现实质问题时，逐项回应并修订交付物。
- 未发现实质问题时，明确写"未发现足以改变结论的实质反证"，并说明已覆盖的反证角度；不得为了凑数虚构漏洞。
- 对流程、SOP、问卷、活动方案或计划，无论核验强度如何都必须做模拟走查：记录执行角色、前置条件、关键步骤、卡点、后果和修复动作。允许并应当暴露"卡壳"，不要演示一个必然顺利的流程。

### 5. 修订后复检

将审核和压力测试中需要采纳的发现纳入交付物后，重新检查：

- 是否产生新的事实、假设、依赖或待核验项；
- 是否仍满足任务对齐单中的完成标准；
- 是否仍存在阻断项。

存在阻断项时，回到阶段②返修。返修后至少重做：

- 对照任务对齐单的自检；
- 针对被修改内容及其新增依赖的独立审核（核验强度 = 加强时）；
- 针对被修改内容及其失败路径的反证与压力测试（核验强度 = 加强时）。

若复审再次出现阻断项，继续按同一规则返修。最多进行 **2 轮完整返修—复审循环**；第 2 轮后仍有阻断项时，停止宣称完成，向用户交付问题清单、已完成内容和需要人工决定或补充的信息。

### 6. 形成核验摘要

不要把审核过程和红蓝对抗混入主正文。交付时在主交付物后附以下摘要；需要时将详细审核表置于附录。

```markdown
## 核验摘要

- 核验强度：基础 / 加强（加强时说明独立审核与反证结论）
- 核验强度变更说明：……（若用户降为基础，或中途升级/拒绝升级，在此说明）

| 已核实 | 待核实 | 工作假设 |
|---|---|---|
| 可定位来源支持的关键事实 | 尚未完成可靠核验、不能当作事实使用的信息 | 为推进方案暂定、需随条件变化调整的判断 |

### 遗留风险与处理
- …

### 发送 / 决策前必核项
- 金额、比例、日期、数量、排名、引用原话；
- 法规、政策、条款、公开承诺；
- 客户、用户、员工、合作方等涉及个人或组织的事实；
- 会改变推荐、资源投入、对外传播或关键决策的外部信息。
```

## 阶段 ④ 交付

仅在阶段③通过后交付：

1. **主交付物**：可直接使用，满足任务对齐单的完成标准。
2. **核验摘要**：说明核验强度、已核实、待核实、工作假设、遗留风险与发送/决策前必核项。
3. **必要附录**：仅在用户需要追溯时提供主张—证据索引、独立审核表、压力测试与修订记录；不要让这些内容淹没主交付物。

交付时必须明确：哪些内容可直接使用，哪些内容必须在发送、发布或据此决策前核验。不得把未经确认、未经核验或受限条件下的产物包装成确定结论。

## 不做的事

- 不自动触发，不替用户判断是否值得进入严谨模式。
- 不将"对齐"拆成独立 skill。
- 不要求用户阅读详细逐步推理过程。
- 不为了红蓝对抗凑固定数量的漏洞。
- 不把待核实信息、工作假设或工具受限下的粗略判断包装为已核实事实。
- 不用岗位任务卡限制对用户任务的理解。
- 不以一次通过替代后续校准：将真实失败、返工或被用户指出的遗漏整理为少量代表性案例，定期检查本技能是否真正降低返工与误判。
