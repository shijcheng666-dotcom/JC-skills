# 技能测试台

## 目标

帮助用户判断候选 Skill 或版本是否在真实任务中带来可观察、可复核、且值得其执行成本的改善。默认只读评估，不修改、安装、覆盖或发布被测 Skill。

评价对象是用户收益，不是候选是否复述了流程、使用了框架名称、产出了更多篇幅或留下了更多文档。

## 先对齐比较目标

开始前，用最少的问题确认：

1. 用户要做的决定：选择版本、诊断问题，还是验证某项改动；
2. 目标使用者、典型任务和不可接受结果；
3. 候选版本及其来源；
4. 可接受的时间与执行成本；
5. 是否需要正式、可归档的结论。

信息不足但可做探索时，说明工作假设后进入快速探索；只有缺少会改变比较对象或验收标准的关键信息时才提问。

## 选择工作层级

| 层级   | 适用场景               | 最小要求                              | 结论边界                          |
| ---- | ------------------ | --------------------------------- | ----------------------------- |
| 快速探索 | 首次判断、低风险筛选、发现方向    | 1 个核心任务 + 1 个边界任务，留存输入、运行记录、产物与限制 | 仅 `exploratory`，不得宣布版本胜负或普遍有效 |
| 标准比较 | 多版本选择、优化决策、需要人工复核  | 差异表、能力卡、任务矩阵、隔离运行、评分与人工阅读包        | 可形成 `directional` 推荐，披露样本与限制  |
| 严格审计 | 版本归档、重要决策、对外或高风险使用 | 冻结设计、可验证证据、状态门禁、盲审包与完整审计记录        | 仅满足全部条件时可为 `decision-ready`   |

除非用户要求正式决策、版本归档或严格审计，默认使用快速探索。不得为满足严谨感而把所有任务强制升级为严格审计。

## 通用实验原则

1. 先创建 `design/capability-card.md`，从用户视角提炼 2-4 个可观察收益或风险。候选内容仅用于理解边界、设计差异任务和形成假设，不得直接定义成功。
2. 多版本先创建差异表。把版本差异、预期影响和待验证问题写清楚，避免同时改变多个变量却做单一归因。
3. 任务至少覆盖核心收益和边界风险。标准比较及严格审计还应覆盖一个可区分候选差异的情境。若差异涉及触发、澄清、确认或交互轮次，必须将其纳入边界任务，而非只比较最终文本。
4. 最终交付质量与过程行为分开评价。流程名称、篇幅、格式复杂度、框架声明和留档本身不得给最终质量加分。
5. 每个结论标明信息状态：`已核实`、`观察到`、`工作假设` 或 `待验证`。小样本只能写“观察到”或“可能相关”，不得直接写“Skill 导致”。
6. 区分产物问题、候选机制问题、执行环境限制和任务设计问题。单个错误不能自动归因于 Skill。

## 全局角色硬门禁

所有任务执行角色和所有盲审角色必须由独立子代理承担。主协调 Agent 不得亲自生成候选任务产物或盲审评分。

每个任务、候选、重试和盲审轮次都必须通过 `task` 工具创建新子代理，并使用 `context: "fresh"`。仅更换目录、切换提示词或复用同一子代理上下文都不满足要求。完整派发、输入边界、结构化返回和核验规则见 `references/execution-protocol.md`。

## 加载与归因边界

优先让执行者真实加载被测 Skill，并记录加载工具成功证据和候选文件指纹。

无法真实加载时，可以比较候选内容的注入效果或基于候选文本做受限观察，但必须明确：结果只能归因于注入方法或候选内容，不能归因于真实 Skill 的加载、触发与工具行为。不得伪装成真实加载实验。

`input.json` 只保存执行者实际可见的用户输入、允许背景、角色与正式确认消息。成功标准、事实账本、评分卡、预期判断、其他候选与私有任务卡仅保存到 `design/`，执行者不得读取。

## 严格状态门禁

严格审计中使用下列状态：

| 状态             | 含义                            | 主汇总 |
| -------------- | ----------------------------- | --- |
| `VALID`        | 输入匹配、材料完整、加载或注入证据完整，关键隔离条件可验证 | 纳入  |
| `LIMITED`      | 可阅读或可评分，但存在未解决限制              | 仅附录 |
| `INVALID`      | 文件缺失、执行失败、哈希不一致或结构错误          | 排除  |
| `CONTAMINATED` | 读取私有标准、其他候选或未声明上下文            | 排除  |
| `SUPERSEDED`   | 已被新单元替代，且有双向引用                | 排除  |

执行者只能记录事实；协调者或验证脚本依据可定位证据判定状态。执行者自报不能单独支持 `VALID`。

## 盲审与跨模型复评

只有在需要匿名比较候选最终质量或过程质量时才创建盲审包。严格双候选盲审使用：

```text
python scripts/prepare_review_pack.py <source-pack> <new-review-pack> --scoring-card <SCORING.md>
python scripts/verify_review_pack.py <review-pack> --expected-hash sha256:...
```

现有脚本只支持每项任务的一对 `CAND-A/CAND-B` 材料。三项以上候选可在标准比较中使用人工盲审或分轮淘汰，并在报告中说明方法；不得把脚本限制伪装成实验结论。

只有能选择并记录与首轮不同的准确模型 ID 时，才可称为跨模型复评。否则提供交接卡，不创建“同模型跨模型复评”。

## 交付

所有层级的最终回复都应直接回答：推荐什么、适用于什么、证据有多强、成本和风险是什么、下一步应做什么。

标准比较和严格审计还应生成 `reviewers/human-review.md`，以真实版本名链接原始对话、产物、状态和排除原因，供使用者人工复核。严格审计的完整目录、冻结与盲审协议见 `references/strict-audit.md`。
