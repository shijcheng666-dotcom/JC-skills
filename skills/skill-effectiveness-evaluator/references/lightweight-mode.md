# 快速探索

## 目的

快速发现候选之间是否存在值得进一步验证的用户收益差异。它适合低风险筛选，不替代正式版本决策。

## 流程

1. 建立简短能力卡：用户要完成什么、预期收益、主要风险和不应作为评分依据的流程痕迹。
2. 列出候选和已知差异；信息不足时标为工作假设，不补写为事实。
3. 先按 `references/task-design-principles.md` 阅读被测 Skill 的实际内容和架构，再设计两个任务：
   - 核心任务：检验 Skill 的主要用户收益；
   - 边界或压力任务：检验 Skill 的薄弱点、易错点、简单任务成本，或版本差异是否影响澄清、确认、触发和交互。
4. 按 `references/execution-protocol.md` 派发每个候选的独立 fresh 执行单元，使用相同输入并保存协议要求的运行材料；优先真实加载，不能真实加载时记录受限观察边界。
6. 从用户收益角度比较任务达成、材料支持度、可用性/返工和效率/用户成本。过程动作可单独记录，但不得直接加到最终质量分。
7. 输出探索结论、反例、限制，以及是否值得升级到标准比较。

## 结论规则

只能使用 `exploratory`。允许的表述包括：

- “在两个任务中观察到候选 A 的交付更直接，值得进入标准比较。”
- “候选 B 在边界任务增加了确认轮次，是否构成真实用户成本仍待复测。”

不得使用：

- “候选 A 胜出。”
- “候选 B 无效。”
- “该 Skill 普遍有效。”

## 最小交付

```text
artifacts/skill-lab/<evaluation-id>/
├── design/capability-card.md
├── design/difference-notes.md
├── inputs/
├── runs/<unit-id>/
│   ├── input.json
│   ├── execution.json
│   ├── transcript.md
│   └── artifact.md
├── reviewers/
│   └── human-review.md
└── REPORT.md
```

快速探索不要求盲审，但人工查看入口仍应链接所有执行子代理的完整对话和最终产物。

`REPORT.md` 依次写：用户决策问题、观察到的差异、按任务的证据、限制、建议的下一步。不要为了轻量模式伪造状态证据、盲审或显著性结论。
